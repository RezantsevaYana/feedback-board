# Роли и закрытые доски — продуктовый план

Сейчас у доски есть владелец (`owner_id`) и команда без ролей (pivot `project_user`), а сама доска всегда открытая: читать, предлагать и голосовать может любой без входа. Этого не хватает двум сценариям студии: внутренние продукты компании (доска только для своих) и клиентские проекты (клиент в команде доски студии).

Документ рассчитан на продолжение в разных сессиях. Внизу чеклист, отмечай пройденное.

**Прототип:** `frontend/demo/roles-prototype.html` — визуальный флоу с блок-схемой и ключевыми экранами. Доступен локально на `http://localhost:5175/roles-prototype.html` и через GitHub.
**Текстовый флоу:** `docs/ROLES_FLOW.md` — пошаговое описание сценариев.

## 1. Продуктовые решения

### Доступ и видимость

- **Видимость доски** — `public` (как сейчас, доступ всем по URL) или `private` (только участникам). Переключение в обе стороны, каждое — с предупреждением о последствиях (обратное `private → public` разрешено 02.11.2026, см. §5).
- **Доступ в закрытую доску — только через участие.** Два способа попасть: получить именное приглашение или подать заявку по URL и получить одобрение админа.
- **Доменов нет.** От авто-входа по домену почты отказались. Для «пригласить 15 коллег разом» — bulk-инвайт (вставить список почт через запятую/строки, выбрать роль, отправить).

### Роли

Пять уровней, назначаются **на доску**. Один человек может быть Владельцем одной доски и Участником другой — хранится в `project_user.role` (enum).

| Роль | Читать | Голос | Пост | Статусы | Настройки | Удалить |
|---|---|---|---|---|---|---|
| Владелец (`owner`) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Админ (`admin`) | ✓ | ✓ | ✓ | ✓ | ✓ | — |
| Менеджер (`manager`) | ✓ | ✓ | ✓ | ✓ | — | — |
| Участник (`voter`) | ✓ | ✓ | ✓ | — | — | — |
| Читатель (`reader`) | ✓ | — | — | — | — | — |
| Гость | только `public` | только `public` | только `public` | — | — | — |

«Статусы» = двигать карточки, менять статусы, скрывать посты, отвечать.

Миграция существующих `project_user`-записей: прежний Admin → `admin`, Team → `manager`, Member → `voter`. Прав не теряем. Владелец переезжает в `project_user` с ролью `owner`, поле `project.owner_id` остаётся как кэш «кто создал».

### Пометки «команда / внешний» нет (решено 28.10.2026)

Сначала была отдельная ось от роли: флаг `is_team_member` у участника и `team_domain` у доски для авто-отметки. Убрали: на доступ и права она не влияла, только рисовала бейдж и добавляла шаг с галочками в приглашение. Всё регулируется ролью. Если понадобится отличать своих от клиентов — вернуть как фильтр или группировку, а не как флаг в форме.

### Приглашения и запросы доступа

- **Инвайт** — письмо на почту с одноразовым токеном (7 дней). Клик по письму → экран принятия со всей информацией (роль, пригласивший, доска) + поля «Имя» и «Пароль» (можно пропустить). Для уже зарегистрированного пользователя — одна кнопка «Присоединиться».
- **Bulk-инвайт** — одна форма принимает список почт (через запятую или по строкам), одна роль для всей пачки. Для микса ролей — отправить несколькими пачками.
- **Запрос доступа по URL** — клиент открывает прямую ссылку на закрытую доску, видит экран-привратник: «Это закрытая доска, запросите доступ». Поля: имя, почта, зачем нужен (опц.). После отправки — короткий экран «Заявка отправлена, ждите письма»; содержимое доски скрыто.
- **Админ** видит ожидающие заявки на доске (в разделе «Участники» + в кабинете). Апрувит inline: выбирает роль из дропдауна, жмёт «Одобрить» → клиент получает письмо с одноразовой ссылкой на вход. Отклоняет с опциональной причиной; после отказа та же почта может попроситься снова только через сутки (решено 30.10.2026 вместо чёрного списка).

### Вход

- **Пароль задаётся на экране принятия приглашения** (или в профиле позже). Пароль **никогда не фигурирует в письмах**.
- **Форма входа одна** для всех ролей и всех досок: почта + пароль + «Войти», ниже — «Забыли пароль?».
- **Rate-limit:** 5 попыток пароля / 10 минут на одну почту → пароль блокируется на 15 минут, разблокировка через смену пароля по письму.
- **Открытие письма** (приглашения или восстановления пароля) = подтверждение почты, отдельного шага нет.
- **Сессия ~30 дней со скользящим продлением** — активные пользователи фактически не разлогиниваются.

### Кабинет (`/app/*`)

Главный экран залогиненного пользователя — список всех его досок, сгруппированных по режиму:

- **«Я веду»** — доски, где я `owner` или `admin`. Управленческий режим: настраиваю, зову, апрувлю заявки.
- **«Я участник»** — доски, где я `manager`, `voter` или `reader`. Рабочий режим.

Нотификационные блоки сверху, скрыты, если пусто:
- 📬 «Вас приглашают» — pending инвайты на мою почту.
- 🔔 «Ждут решения на ваших досках» — pending access_requests на досках, где я Owner/Admin.

Публичные доски, где я не Owner/Admin, в кабинете не показываются — на них я прихожу по URL.

### Голоса на закрытой доске

Привязаны к аккаунту: один человек — один голос. Счётчик видят все с доступом. Список голосовавших — только команда доски (Owner/Admin/Менеджер); Участники/Читатели видят только число.

На открытых досках голоса остаются анонимными, как сейчас.

### Копирайт писем и переходных экранов

Не фиксирует назначение доски. Сервис используют по-разному: одни — для багов, другие — для идей, третьи — для внутренних обсуждений, четвёртые — для клиентских претензий. Поэтому в приглашении, запросе доступа, экране ожидания:

- **Не пишем** «обратная связь по продукту», «идеи», «баги» как единственный смысл доски.
- **Пишем** «рабочая доска команды» + перечисляем через запятую возможные типы содержимого («идеи, баги, запросы, обсуждения») — чтобы ни один сценарий не выглядел главным.
- **Специфические термины** появляются только внутри самой доски, через категории, которые завёл её владелец.

## 2. Сценарии

Четыре основных флоу доступа (цветовое кодирование совпадает с прототипом).

- **A. Приглашённый из команды** (зелёный). Админ отправил инвайт сотруднику → письмо → экран принятия с именем + паролем → доска.
- **B. Приглашённый клиент** (синий). Тот же флоу, что A, но роль обычно Участник или Читатель, бейдж «внешний».
- **C. Клиент по прямой ссылке** (оранжевый). Открыл URL → экран-привратник → форма «Запросить доступ» → заявка → админ одобряет inline с выбором роли → письмо «одобрено» с одноразовой ссылкой → доска.
- **D. Повторный вход** (розовый). Форма: почта + пароль; при забытом пароле — восстановление по письму.

### Этап 4+. Отложено

- **Пространства (workspace).** Один человек присоединяется к пространству, получает роль на всех его досках сразу. Появится, когда клиентских досок станет много и ручное управление станет болью.
- **SSO в виджете.** Сервер продукта подписывает email пользователя секретом доски, виджет узнаёт человека без логина (как у Canny / Featurebase). Нужно для закрытых досок, встроенных в чужой SaaS.
- **Передача владения.** В V1 — через ручной бэкофис по тикету.
- **Блокировка почты на доске («Отклонить и забанить»).** Было сделано и убрано 30.10.2026: в V1 отказ закрывает повторные заявки на сутки, этого хватает. Вернуть, если на какую-то доску пойдёт настоящий спам заявками. Что понадобится: таблица `project_access_blacklist` (project_id, email, created_by), кнопка «Отклонить и забанить» через подтверждение без письма, проверка в `Public\AccessRequestController::accepts()`, и сразу — список забаненных с кнопкой «Разбанить» в участниках (без неё ошибочный бан не исправить).
- **Одобрение запроса сразу добавляет на доску + одноразовая ссылка на вход.** Так было в исходном плане этапа 3. Сейчас одобрение выдаёт приглашение, и человек попадает в `project_user`, только приняв его (см. «Решения в ходе работы», 30.10.2026). Вернуться, если шаг «принять приглашение» после одобрения окажется лишним для клиентов. Что понадобится: вернуть одноразовый вход по ссылке (magic-link, см. решение от 29.10.2026 и commit до отката) и решить, что делать с почтой без аккаунта: создавать аккаунт при одобрении или при первом входе по ссылке. Ещё учесть, что заявку может подать кто угодно с чужой почтой: при сразу-добавлении доступ получает владелец ящика, даже если он ничего не просил.

## 4. Что НЕ входит в V1 (решено явно)

- Домены почты как канал доступа: ни авто-входа, ни авто-пометок по домену.
- Отправка пароля в теле письма (безопасность).
- **Magic-link / passwordless entry.** В этап 2 попробовали (миграция `magic_links`, контроллер, письмо, страница приёма, 10 тестов — всё было зелёное), 29.10.2026 откатили. См. блок «Решения в ходе работы» ниже.
- Wildcard-домены, разные роли по доменам.
- Передача владения, восстановление доски после ухода владельца.
- SSO в виджете (отложенный этап 4).
- Пространства / workspace (отложенный этап 3+).
- Автоудаление доступа ex-сотрудника автоматически (кроме отключения почты IT-отделом → magic-link перестаёт приходить).
- Лимиты на число участников / тарификация.

## 5. Решения в ходе работы

- **Magic-link убран (29.10.2026).** Начали реализацию: таблица `magic_links` (sha256-хеши ссылки и кода, TTL 15 мин, 5 попыток, partial unique по почте), `MagicLinkController@request/consume`, письмо с ссылкой + 6-значным кодом, страница `/app/magic-link/:token`, кнопка «Прислать ссылку на почту» на `LoginPage`, 10 feature-тестов — всё прошло. При ревью решили: сценарии V1 не требуют второго пути входа. Приглашённый задаёт пароль прямо на экране принятия инвайта; забывший — восстанавливает по письму; клиент по URL проходит через «запросить доступ → одобрение → стандартный логин». Magic-link дублирует существующий `/app/forgot-password`-флоу и добавляет поверхность атак (брут 6-значного кода, спам по почте). Весь код удалён, прототип и чеклист выровнены. При возврате: см. commit до отката.
- **Пауза в сутки после отказа вместо чёрного списка (30.10.2026).** Отказ с письмом закрывает новые заявки с этой почты на эту доску на 24 часа; молча, ответ формы не меняется. Чёрный список убран из кода, бан — в отложенном.
- **Видимость доски видна (30.10.2026).** Значок «Открытая / Закрытая» (`VisibilityBadge`) в карточке доски в кабинете и под названием доски в её сайдбаре; на планшете и телефоне — только иконка (глобус / замок), текст в подсказке и для скринридеров.
- **Одобрение запроса доступа = приглашение (30.10.2026).** План этапа 3 говорил «одобрение создаёт запись в `project_user` и шлёт одноразовую ссылку на вход», но одноразовой ссылкой на вход был magic-link, а его убрали. Поэтому одобрение выдаёт приглашение с выбранной ролью, письмо «Доступ к доске открыт» ведёт на обычный экран принятия `/app/invite/{token}`, а запись в `project_user` появляется при принятии. Второго пути входа нет. Исходный вариант отложен в «Этап 4+. Отложено».

- **Закрытую доску можно открыть обратно (02.11.2026).** В V1 переход был односторонним: на закрытой доске пишут, рассчитывая, что видят только свои. Решили разрешить, но с предупреждением, что именно станет видно. Сценарии (они же — список в «Настройки → Доступ» и тест `VisibilityTest::test_private_board_opens_back_with_its_votes`):
  - **Посты.** Всё, что написано на доске, видно любому по ссылке: посты, ответы команды, имена авторов из аккаунтов. Скрытые посты остаются скрытыми.
  - **Голоса участников** сохраняются и остаются привязаны к аккаунтам (`votes.user_id`): счётчики не меняются, участник с любого устройства видит свой голос и может его снять.
  - **Голоса гостей** с открытия снова принимаются — анонимно, по токену браузера, — и прибавляются к тем же счётчикам. «Кто голосовал» по-прежнему видит только команда; гостевые голоса там анонимные.
  - **Участники и роли** остаются. Приглашения действуют. Читатель, вошедший в аккаунт, по-прежнему не голосует (как и на любой открытой доске).
  - **Запросы на доступ**, ждущие ответа, не трогаем: они пригодятся, если доску снова закроют. Писем никому не шлём.
  - **Виджет** снова принимает предложения от гостей с разрешённых доменов.
  - **Подтверждение:** «Открыть доску для всех?» с числом постов, которые станут видны. Закрыть снова можно в любой момент.

- **Роль `voter` называется «Участник» (02.11.2026).** «Голосующий» читался как «только голосует», а роль ещё и предлагает. Код роли (`voter`) не меняли, только подпись: `ROLE_LABELS`, письма, ошибки валидации, прототип, чеклист.

## 6. Открытые вопросы

- **«Кто голосовал» для рядовых участников.** Пока команда видит, Участники/Читатели — только счётчик. Если команда решит раскрыть — поменять флаг.
- **Переключатель досок в хедере самой доски.** В V1 не делаем, достаточно возврата в кабинет. Если станет неудобно — добавим дропдаун.
- **Что делать, если у студии несколько клиентов делят одну доску** (аутсорс-команда ведёт N продуктов). Не для V1, но стоит проверить, не ломает ли нас «один владелец = одна студия».
