Роли и доступ к доскам

Прототип флоу: как люди попадают на закрытую доску (приглашение, запрос доступа), какие роли бывают, что видит админ, что видит участник. Решения, помеченные как «моё предложение», открыты для спора.

1Сценарии

Четыре флоу доступа. На схеме ниже они окрашены этими же цветами, экраны в разделе 4 помечены тем же бейджем.

A — Приглашённый из команды
Админ отправил инвайт сотруднику. Тот открывает письмо, задаёт имя+пароль, попадает на доску.
B — Приглашённый клиент
Тот же инвайт, но роль Голосующий или Читатель. Приглашает Owner/Admin вручную.
C — Клиент по прямой ссылке
Увидел URL доски. Доска закрыта. Жмёт «Запросить доступ» → админ одобряет → письмо → вход.
D — Повторный вход
Сессия истекла или человек с нового устройства. Пароль или magic-link.

Решения, зафиксированные в прототипе

  • Доменов больше нет. Доступ в закрытую доску — только по инвайту или через апрув запроса. Для 15 коллег начальник использует bulk-инвайт (вводит список почт разом).
  • Пять ролей: Владелец, Админ, Менеджер (двигает карточки, не настраивает доску), Голосующий, Читатель. Разделение «Голосующего» и «Читателя» даёт тонкую настройку для клиентов и наблюдателей.
  • Роль задаётся на доску. Один человек на доске A — Менеджер, на доске B — Читатель. Хранится в project_user.role.
  • Бейдж «команда / внешний» рядом с именем в списке участников. Два поля в БД, независимо от роли:
    • project.team_domain — одна plain-строка. При создании доски система кладёт туда домен владельца (ivan@rocont.ru → rocont.ru). Публичные домены (gmail, outlook и т.п.) → null. Владелец может поменять в настройках.
    • project_user.is_team_member — булев флаг на связке «человек × доска». При приглашении пред-заполняется автоматически (домен совпал с team_domain → true, иначе false). Можно переопределить в форме инвайта и позже в списке участников — не меняя роль.
    Доступ на доску не зависит от домена, флаг влияет только на визуальную группировку.
  • Пароль задаётся на экране принятия приглашения (можно пропустить и ходить по ссылке). В письме пароля нет.
  • Клиент по URL не видит содержимое доски до одобрения — только форму запроса и экран «Заявка отправлена, ждите письма». Админ выбирает роль при одобрении.
  • Апрув заявки — inline в карточке запроса, без отдельного экрана.
  • Один пользователь — множество ролей. Человек может быть Владельцем одной доски и Голосующим другой. В кабинете — две группы: «Я веду» (Owner/Admin) и «Я участник» (Менеджер/Голосующий/Читатель). См. экран 4.10.

3Роли и права

Пять уровней доступа. Назначается на конкретную доску при приглашении или апруве. Можно менять в любой момент из списка участников (сценарий 4.9).

Роль Читать Голосовать Писать посты Двигать карточки (триаж) Настройки / инвайты Удалить доску
Владелец ✓✓✓✓✓✓
Админ ✓✓✓✓✓—
Менеджер ✓✓✓✓——
Голосующий ✓✓✓———
Читатель ✓—————

Решения по ролям

  • Менеджер vs Админ — обе роли. Менеджер двигает карточки и ставит статусы, но не трогает настройки и не зовёт людей. В клиентских проектах это та же роль, что у «джуниора команды», которому доверили разбор. Админ — редкая делегированная роль (например, старший PM на клиентском проекте), который может звать людей и менять настройки.
  • Читатель — оставляем. Для наблюдателей: продакт соседней команды, стажёр, легал на ревью. Клиенту по умолчанию ставим Голосующий.

4Ключевые экраны

Группами по сценариям. Каждый экран подписан бейджем сценария и ID (4.N).

4.1 — Письмо приглашения

Кому: masha@rocont.ru

Это рабочая доска команды. Что в неё писать — решает команда: идеи, баги, запросы, обсуждения. Вы сможете создавать посты, голосовать и двигать карточки между статусами.

A/B · 4.1

Письмо приглашения

Одно письмо и для участника команды, и для клиента. Отличие — только роль в тексте («как Менеджера» / «как Голосующего» / «как Читателя»).

  • Токен в ссылке, живёт 7 дней, одноразовый.
  • Пароля в письме нет: пользователь задаст сам на следующем экране.
  • Копирайт не фиксирует назначение доски. Разные команды пользуются по-разному: кто-то для багов, кто-то для идей, кто-то для внутренних обсуждений. Пишем «рабочая доска команды» + перечисление через запятую («идеи, баги, запросы, обсуждения»), чтобы ни один сценарий не казался главным.

Принятие приглашения — новый пользователь

Единственный одношаговый экран онбординга. После клика:

  • Создаётся аккаунт, почта помечена подтверждённой.
  • Сохраняется имя и хэш пароля.
  • Записывается в project_user: роль, invited_by, source=invite.
  • Токен сжигается.
  • Пользователь сразу залогинен и редиректится на доску.
Если «Пропустить пароль»: аккаунт создаётся без пароля, вход только по magic-link. Пароль можно задать позже в профиле.

Принятие приглашения — существующий аккаунт

Частый случай у команды студии: сотрудник уже зарегистрирован в системе (есть другие доски), владелец приглашает на новую доску.

  • Если залогинен и почта совпадает с инвайтом — одна кнопка.
  • Если залогинен другой почтой — ссылка «войти как другой» переключает сессию.
  • Пароль не трогаем, имя не трогаем — только добавляется запись в project_user.

Закрытая доска: запрос доступа

Клиент получил ссылку (от менеджера, из переписки, с сайта продукта) и открыл её. Доски не видит, вместо неё — экран-привратник.

  • Поле «Зачем нужен доступ» не обязательное, но повышает шанс одобрения — об этом подсказка.
  • Если у клиента уже есть аккаунт в системе (бывает редко, но возможно): ссылка «войти» — на обычный логин, после входа сразу редирект на эту же доску, которая всё равно закрыта → всплывёт та же форма запроса, уже с подставленными имя/почта.
  • Создаётся запись access_request (project_id, email, name, message, status=pending, created_at).
Что видит клиент сразу после отправки: короткий экран «Заявка отправлена, ответ придёт на klient@externalcorp.com». Содержимое доски по-прежнему скрыто.

Раздел «Запросы на доступ»

Приходит в раздел «Участники». Над списком участников — секция ожидающих запросов, с цифрой в табе.

  • Админ выбирает роль из дропдауна (дефолт — Голосующий, самое безопасное для нового клиента).
  • «Одобрить» → запись переезжает в project_user с выбранной ролью, статус запроса меняется на approved, уходит письмо.
  • «Отклонить» — просит причину (необязательно), уходит письмо.
  • «Отклонить и забанить» для спама — почта попадает в чёрный список доски, повторные запросы автоматически блокируются.
Нотификация: письмо админу приходит сразу + индикатор в табе «Участники» на доске (красный бейдж с числом ожидающих).

Письмо об одобрении

Приходит клиенту сразу после одобрения.

  • Содержит одноразовую ссылку (как magic-link, 7 дней): клик → автоматический логин → доска.
  • Прямо упоминается роль, чтобы клиент понял, что ему доступно.

Форма приглашения

Один флоу для одного человека и для 50 — просто пишешь список.

  • Авто-определение «команда»: для каждой почты система сравнивает домен с project.team_domain (сюда записывается домен владельца при создании доски). Совпал — чекбокс пред-отмечен, иначе — нет. В обоих направлениях переопределяется.
  • Валидация почт на лету; невалидные подсвечены красным, они не отправляются.
  • Роль одна для всей пачки. Для микса — отправить отдельно (один инвайт с ролью Менеджер для команды, второй с Голосующим для клиента).
  • Сопроводительный текст — опционально, идёт в тело письма дополнительным блоком.
  • Кнопка показывает число — «Отправить 4 приглашения».
Если team_domain = null (владелец доски на gmail или не вписал домен в настройках): все чекбоксы по умолчанию выключены, админ ставит руками. Подсказку о «домене команды» заменяем на «домен команды не задан — задайте в настройках, чтобы работало автоматически».
Что если такая почта уже на доске: подсветить в списке «уже участник, роль …», не отправлять ей инвайт.

Повторный вход

Одна форма для всех ролей и для всех досок. Основной путь — пароль + «Войти».

  • «Прислать ссылку на почту» → magic-link флоу: 6-значный код + одноразовая ссылка, 15 мин.
  • «Забыли пароль?» → отдельный флоу восстановления (письмо со ссылкой на смену пароля, 1 час).
  • Если пароль неверный и у человека его в системе нет — сразу показываем «вы не задавали пароль, войдите по ссылке».
  • Rate-limit: 5 попыток / 10 мин → пароль блокируется на 15 минут, magic-link продолжает работать.

Список участников и управление ролями

Один экран для всех трёх сценариев: приглашённые команды, приглашённые клиенты, одобренные по запросу — все в одной таблице.

  • Смена роли — дропдаун прямо в ячейке, без модалки. Клик → меняется мгновенно, подтверждение не нужно, но есть «отменить» в тосте 10 секунд.
  • Бейдж «команда / внешний» выводится из is_team_member, которое задаётся на инвайте и редактируется кликом по бейджу. Это не роль — сотрудник может быть Голосующим и оставаться «командой», клиент может быть Админом и оставаться «внешним».
  • Источник — короткая подпись под датой: «по инвайту», «по запросу», «создал доску». Нужна для аудита (кого откуда).
  • Ожидающие приглашения — с жёлтым статусом «не принято» в колонке имени. В меню «⋯» — переслать, отменить.
  • Меню «⋯» на строке: «Удалить из доски», «Переслать приглашение» (для не принятых), «Сбросить пароль» (прислать письмо восстановления).
Что видят не-админы: та же таблица, но без дропдаунов роли (только пилюля), без клика по бейджу (только отображение), без меню «⋯», без email (только имя + роль + бейдж). См. ветку доступа в ROLES_PLAN.md.

Кабинет: мои доски и разные роли

Главный экран, куда попадает залогиненный пользователь. Один человек может быть владельцем на одних досках и просто участником на других — хаб показывает всё в одном месте.

  • Группировка «Я веду / Я участник» — две разные ментальные модели. В верхней группе — доски, где я решаю (Owner или Admin). В нижней — куда меня пригласили просто участвовать.
  • Пилюля роли справа — моя роль именно на этой конкретной доске. Один и тот же человек на разных досках может иметь любую комбинацию.
  • Бейдж «команда / внешний» — только для досок из группы «Я участник». Он отвечает на вопрос: «эта доска моего работодателя (команда) или я туда зашёл как гость?». Для досок из группы «Я веду» бейджа нет, потому что ты и есть эта команда.
  • Нотификационные блоки сверху:
    • 📬 Инвайты, которые жду я (пригласили, но ещё не принял).
    • 🔔 Запросы на мои доски (где я Admin/Owner и кто-то ждёт одобрения).
    Обе секции скрываются, если нулевые.
  • Иконки видимости (🔒 / 🌐) — открытая или закрытая доска. Нужно, потому что в кабинете у Owner обычно смесь.
  • Клик по карточке → страница самой доски (её URL).
  • «+ Создать доску» → короткая форма (название, видимость, slug). После создания — автоматически Владелец, попадает в раздел «Я веду».
Что про смену контекста: на самой доске сверху — тот же бренд «Feedback Board» слева, при клике — возврат в кабинет. Отдельного «переключателя досок» в хедере доски не делаем в V1 (достаточно вернуться в хаб). Если станет неудобно — добавим дропдаун.
Публичные доски: в кабинете видны только если ты их Owner/Admin. Как Голосующий/Читатель на публичной доске тебя не отслеживаем, туда ты заходишь просто по URL.

5Решения по итогам обсуждения

Эти развилки прошли через обсуждение и зафиксированы. При необходимости — возвращаемся.

  • Пять ролей — оставляем. Менеджер (разбор без настроек) и Голосующий (без разбора) — разные кейсы, разделение полезно для клиентских проектов.
  • Роль «Менеджер» — новое название вместо «Триажер». Короткое, понятное без контекста, в твоём направлении «менеджер доски».
  • Читатель — оставляем. Отдельный уровень «только читать, без голоса» для наблюдателей.
  • После запроса доступа клиент видит короткий экран «Заявка отправлена, ждите письма». Содержимое доски скрыто, превью нет.
  • Админ одобряет inline — кнопка на карточке запроса, без отдельного экрана. Для спама — «Отклонить и забанить».
  • Лимитов на число участников в V1 нет. Тарификация и платные планы — не раньше, чем появятся платящие.
  • Бейдж «команда / внешний» в UI есть, независимо от роли. В БД два поля:
    • project.team_domain — одна строка, кладётся при создании доски из домена владельца (gmail-подобное → null). Правится в настройках.
    • project_user.is_team_member — булев флаг на каждой записи. При инвайте авто-пред-заполнение по совпадению домена; при любой заявке можно переопределить вручную в форме и в списке участников.
    Доступ на доску от этих полей не зависит, они нужны только для группировки.
